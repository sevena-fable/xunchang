# 04 · 技术方案与数据库设计

## 技术栈

| 层级 | 技术 | 作用 |
|------|------|------|
| 前端框架 | React + Vite | 页面与交互 |
| 样式 | Tailwind CSS | 快速写出统一的界面样式 |
| 动画 | Framer Motion | 鸽子飞行、开信、领养等动画 |
| 音频 | Howler.js | 环境音播放 |
| 后端 | Supabase | 一站式:认证 + 数据库 + 存储 + 实时推送 |
| 数据库 | PostgreSQL(Supabase 托管) | 所有数据 |
| 部署 | Vercel | 前端托管,免费额度足够 |

### 为什么用 Supabase(而不是自己写后端)

- 创建数据库表 → 自动获得 API,不用写后端代码
- Supabase Auth 自带邮箱注册/登录
- Supabase Realtime:数据一变,对方页面自动收到推送——**鸽子位置同步、信件送达、召唤许可**全靠它
- Supabase Storage 存信里的图片
- 免费额度(500MB 数据库 / 1GB 存储)对两个人的产品绰绰有余

## 架构图(文字版)

```
浏览器(React 前端)
  ├── 窗台场景(四时画面、物件、鸽子)
  ├── 写信 / 开信 / 回应 / 日历 组件
  ├── Framer Motion(动画) + Howler.js(环境音)
  └── Supabase JS Client
        │  REST API + Realtime(WebSocket 实时推送)
        ▼
Supabase
  ├── Auth(邮箱+密码)
  ├── PostgreSQL(数据表)
  ├── Storage(信件图片)
  └── Row Level Security(确保只有配对双方能看到自己空间的数据)
```

## 数据库表设计

### profiles — 用户资料

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | = auth.users.id |
| nickname | text | 用户昵称 |
| created_at | timestamptz | |

### pairs — 配对空间

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | |
| invite_code | text | 唯一邀请码 |
| user_a | uuid | 创建者 |
| user_b | uuid | 加入者(未加入时为空) |
| status | text | waiting / paired |
| created_at | timestamptz | |

### pigeons — 信鸽(每个空间一只)

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | |
| pair_id | uuid | 所属空间 |
| name | text | 共同商定的名字 |
| call_for_a | text | 鸽子对 A 的称呼(A 设置) |
| call_for_b | text | 鸽子对 B 的称呼(B 设置) |
| location | text | a_window / b_window |
| state | text | idle(空闲) / delivering(送信中) / guarding(守信) |
| guarding_letter_id | uuid | 守信时守的是哪封信(可空) |
| updated_at | timestamptz | |

### letters — 信件

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | |
| pair_id | uuid | |
| sender_id | uuid | 写信人 |
| content | text | 信件文字 |
| image_urls | text[] | 图片(存 Storage,这里存链接) |
| stationery | text | 信纸款式 |
| status | text | sealed(已封存) / delivering / delivered(已送达) / read(已读) |
| sealed_at / delivered_at / read_at | timestamptz | 各节点时间 |

### reactions — 回应(每封信最多一条)

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | |
| letter_id | uuid | **唯一约束**:一封信只能有一条回应 |
| reactor_id | uuid | 必须是收信人 |
| emoji | text | coffee / heart / like / doge(可空) |
| comment | text | ≤20 字(可空) |
| created_at | timestamptz | 提交后不可修改 |

### summon_requests — 召唤请求(对方在线需许可的场景)

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uuid | |
| pair_id | uuid | |
| requester_id | uuid | 摇铃的人 |
| status | text | pending / approved / rejected / expired / cancelled |
| created_at / resolved_at | timestamptz | |

> 日历不需要单独的表:直接按日期查询 letters 即可(有信的日子 = 标记小信封)。

## 安全:Row Level Security(RLS)

所有表启用 RLS,策略核心只有一条:

> **只有该 pair 的 user_a 或 user_b 能读写这个空间的数据。**

这是双人私密产品最重要的安全保障,任何新表都必须先写 RLS 策略再上线。

## Realtime 实时订阅

前端订阅三类变化:

| 订阅对象 | 用途 |
|----------|------|
| pigeons | 鸽子位置/状态变化 → 双方画面同步(飞走/飞来动画) |
| letters | 新信送达 → 收信人在线时播放鸽子飞来动画 |
| summon_requests | 召唤许可弹窗(对方摇铃了 → 你收到"是否放鸽子回去"的提示) |

## 在线状态判断

"对方是否在线"影响召唤和送达逻辑,使用 Supabase Realtime 的 **Presence** 功能:用户打开页面即标记在线,关闭即离线。

## 溜达机制的实现思路

鸽子的"自主溜达"不需要服务器定时任务:采用**惰性计算**——任一用户上线/操作时,根据"距离上次位置更新过了多久 + 概率规则"结算鸽子当前应该在哪。这样免费方案就能实现,也避免了复杂的后台任务。
